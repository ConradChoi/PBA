# 개인정보 노출 사고 기록 (2026-09-23)

개인정보 보호법에 따른 내부 사고 기록입니다. 이 문서는 사실관계와 조치 내역을 남기기 위한 것으로, 법적 판단(통지·신고 의무)의 최종 확정은 변호사 검토를 전제로 합니다.

## 1. 인지

- **인지 일시:** 2026-09-23 오전 (한국 시간)
- **인지 경위:** 다국어 기능 개발 중 어드민 화면을 점검하다가, 로그인 쿠키 없이 보낸 요청의 응답에 진단 데이터가 포함된 것을 확인. `curl`로 재현해 운영 환경에서도 동일함을 확인함.
- **확인 방법:** `curl https://pba.ylia.io/admin/assessments` → HTTP 307(로그인 페이지로 리디렉션) 응답의 본문에 진단 목록 데이터 포함.

## 2. 발생 기간

- **시작:** 2026-09-18 (어드민 패널 최초 배포일)
- **종료:** 2026-09-23 (수정 배포 완료 시점)
- **기간:** 약 5일

## 3. 원인

두 가지 결함이 겹쳐 발생했습니다.

1. **인증 미들웨어가 실행되지 않음.** `middleware.ts`가 저장소 루트에 있었으나, 이 프로젝트는 소스를 `src/` 아래에 두므로 Next.js는 `src/middleware.ts`만 로드합니다. 루트 파일은 무시되어 어드민 로그인 검사가 한 번도 실행되지 않았습니다. 빌드 출력에 `Middleware` 항목이 없었던 것이 근거입니다(수정 후에는 표시됨).
2. **리디렉션 응답 본문에 렌더링 결과가 포함됨.** 어드민 레이아웃은 로그인 여부를 확인해 `redirect("/admin/login")`을 호출하지만, Next.js는 레이아웃과 하위 페이지를 병렬로 렌더링합니다. 하위 페이지가 이미 데이터를 조회·렌더링한 뒤 리디렉션이 발생해, 그 결과가 307 응답의 본문에 실려 전송되었습니다.

브라우저로 접속하면 로그인 화면으로 이동했기 때문에 화면상으로는 정상으로 보였고, 응답 본문을 직접 확인하는 방법(curl, 개발자도구 네트워크 탭, 크롤러)으로만 노출되었습니다.

## 4. 노출 항목

| 화면 | 노출된 정보 |
|---|---|
| `/admin/assessments` (목록) | 진단일, 이름, 이메일, 사업 단계, 진단 등급, 점수 |
| `/admin/assessments/<id>` (상세) | 위 항목 + 회사명, 역할, 업종, 팀 규모, UTM 유입 정보, 개인정보·마케팅 동의 여부, 결과 적합도, 매출·성장 구간 |
| `/admin/consulting-requests` (목록·상세) | 상담 신청자 이름, 이메일, 상담 메시지 |
| `/admin/notices` | 운영자가 작성한 공지 (개인정보 아님) |
| `/admin/operators` | **노출되지 않음.** 이 화면은 데이터 조회 전에 owner 권한을 확인하는 구조였음 |

수집하지 않는 정보이므로 노출되지 않은 항목: 주민등록번호 등 고유식별정보, 비밀번호, 결제정보, 민감정보.

## 5. 영향 범위

- 사고 시점 데이터베이스의 진단 레코드 7건, 이 중 이름·이메일이 저장된 건 3~4건.
- 해당 레코드는 대표 본인과 지인의 테스트 진단으로 확인됨. 사고 기간 중 외부 홍보를 하지 않아 일반 이용자 유입은 없었음.
- **사업자 판단(2026-09-23):** 노출 대상이 본인 및 테스트 데이터이므로 정보주체 통지는 수행하지 않기로 함.

## 6. 외부 접근 여부

- **확인 가능한 수단:** AWS Amplify Hosting 액세스 로그. 별도 설정 없이 항상 기록되며, **앱을 삭제할 때까지 보관**된다(AWS 문서 기준). 콘솔에서 한 번에 조회할 수 있는 구간이 2주로 제한될 뿐 보관 기간이 2주인 것은 아니다. 따라서 사고 기간(2026-09-18 ~ 09-23)의 기록은 현재도 조회 가능하다.
  - 조회 경로: Amplify 콘솔 → 해당 앱 → Monitoring → Access logs → Edit time range.
- **확인 불가:** GA4(어드민 경로 미추적), Supabase 로그(보존 기간 경과분).
- **사업자 판단(2026-09-23):** 노출 대상이 본인 및 테스트 데이터이므로 로그 분석은 수행하지 않기로 함. 단, 위와 같이 원본 로그는 보존되어 있으므로 필요 시 사후 확인이 가능하다.
- **기록 정정(2026-09-24):** 최초 작성 시 Amplify 액세스 로그의 보관 기간을 "약 2주"로, CloudFront 표준 로그를 "미활성"으로 기재했으나 이는 사실과 다름. 위 내용이 정확한 사실이다.
- 검색엔진 색인 여부: `/robots.txt`가 없었고 어드민 경로에 `noindex`가 없었으므로 이론상 수집 가능했음. 수정 배포에서 두 가지 모두 적용함.

## 8. 재발 방지

1. **누출 검사 자동화** (`scripts/check-admin-no-leak.mjs`): 빌드된 앱을 실행해 인증 없이 어드민 경로 9곳을 요청하고, **응답 본문**에 이메일·이름·진단등급 문자열이 포함되면 실패. `amplify.yml` 빌드 단계에 연결되어 있어 누출이 있는 빌드는 배포되지 않음. 상태 코드만 검사하면 이번 사고를 잡지 못하므로 본문을 검사함.
2. **미들웨어 위치 검사** (`src/middleware.guard.test.ts`): 루트에 `middleware.ts`가 생기거나, `src/middleware.ts`가 없거나, matcher가 `/admin/:path*`를 벗어나면 테스트 실패.
3. **다층 방어:** 미들웨어는 1차 방어선으로만 취급하고, 각 어드민 페이지가 데이터 조회 **이전에** 인증을 확인함.
4. **검색엔진 차단:** 어드민 경로에 `X-Robots-Tag: noindex, nofollow`(`next.config.ts`, `customHttp.yml`)와 `robots.txt` 차단 적용.

검증: 결함을 의도적으로 되살려(미들웨어를 루트로 이동 + 인증 검사 주석 처리) 검사 스크립트를 실행한 결과, 307 응답 본문에서 실제 이름·이메일·진단등급이 출력되며 실패함을 확인한 뒤 원상복구함.

## 9. 남은 과제

- 액세스 로그는 이미 상시 기록·보관되고 있으므로 활성화 작업은 불필요하다. 다만 콘솔에서 2주 단위 수동 조회만 가능하므로, 실제 이용자가 유입된 뒤에는 (a) 정기적으로 내려받아 S3에 적재하고 Athena로 조회하는 경로를 만들어 둘 것, (b) 어드민 경로에 대한 비정상 접근을 사람이 눈으로 찾지 않아도 되도록 알림 기준을 정할 것.
- 결과 페이지 URL에 진단 UUID가 포함되고, 액세스 로그는 URL을 평문으로 남긴다(AWS 문서의 명시적 경고). 이 UUID는 사실상 해당 결과 페이지의 접근 토큰이므로, 로그를 외부(분석 도구·협력사 등)와 공유할 때는 GA4에 적용한 것과 같은 마스킹을 거칠 것.
- Supabase RLS를 최종 방어선으로 검증하는 테스트 추가 검토(현재 서버는 service role 키로 접근하므로 RLS가 우회됨).
