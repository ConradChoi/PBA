# Multi-language (i18n) Design

**Status:** Approved for planning
**Builds on:** the public diagnose flow, result/consult pages, privacy policy page, and shared UI components (`ChipGroup`) as of commit `574f7e3`

## Goal

Serve every public page in Korean, English, Simplified Chinese, Traditional Chinese, and Japanese, picked automatically per visitor, **without changing any URL**. The admin panel stays Korean.

## Decisions Made During Brainstorming

1. **Scope: public pages only.** Landing, `/diagnose` (basic info + question wizard), result, consult, not-found pages, `/privacy`, and the site header/footer. `/admin` stays Korean.
2. **Five locales:** `ko` (default), `en`, `zh-CN` (Simplified), `zh-TW` (Traditional), `ja`.
3. **Same URL for every language.** No `/en/...` prefixes. The locale is decided per request on the server. Trade-off accepted: search engines index one language (Korean), and a shared result link opens in the recipient's language.
4. **Locale decision order:** manual choice cookie → browser language (`Accept-Language`) → visitor country → Korean.
5. **Library: `next-intl`** in its "without i18n routing" mode (no locale segment, no next-intl middleware). Chosen over i18next (more wiring for App Router server components) and hand-rolled dictionaries (reimplementing locale plumbing).
6. **Translations are drafted by Claude and published without separate native review.** Compensating control: every locale file must type-check against the Korean source, so a missing or misspelled key fails the build.
7. **Google Cloud Translation API was considered and rejected**: runtime translation adds latency, an external failure point, and a server key while still needing all the locale plumbing; one-off generation offers no quality advantage over Claude-drafted files.
8. **Company info:** Korean on `ko`; English on all other locales (see section D).
9. **Language switcher is a custom dropdown**, never a native `<select>`: it opens anchored directly under its trigger, renders identically on PC and mobile, and never overflows the viewport.

## A. Locale Decision

Implemented as a pure function in `src/i18n/locales.ts` so it can be unit-tested without a request:

```ts
resolveLocale({ cookie, acceptLanguage, country }): Locale
```

1. **Cookie `NEXT_LOCALE`** — set by the language switcher. If it holds a supported locale, use it.
2. **`Accept-Language`** — walk the list in q-value order; the first entry that maps to a supported locale wins (`fr, en;q=0.8` → `en`). Chinese mapping:
   - `zh-CN`, `zh-SG`, `zh-Hans*`, bare `zh` → `zh-CN`
   - `zh-TW`, `zh-HK`, `zh-MO`, `zh-Hant*` → `zh-TW`
   - Other entries match on their primary subtag (`en-GB` → `en`, `ja-JP` → `ja`, `ko-KR` → `ko`).
3. **Country** — the `CloudFront-Viewer-Country` request header, only consulted when step 2 found nothing: `KR` → `ko`, `JP` → `ja`, `CN`/`SG` → `zh-CN`, `TW`/`HK`/`MO` → `zh-TW`, any other country → `en`.
4. **Nothing usable** (no cookie, no/unsupported `Accept-Language`, no country header) → `ko`. Search crawlers typically land here, which keeps Korean indexing intact.

Whether AWS Amplify forwards `CloudFront-Viewer-Country` to the SSR runtime is **unverified**; it's checked after deployment (section G). If it isn't forwarded, step 3 is simply skipped — steps 1, 2 and 4 still work.

`src/i18n/request.ts` (next-intl's `getRequestConfig`) reads the cookie and headers via `next/headers`, calls `resolveLocale`, and loads that locale's messages.

**Caching:** responses for public pages send `Vary: Accept-Language, Cookie, CloudFront-Viewer-Country` (via `next.config` `headers()`), so CloudFront never serves one locale's HTML to another visitor.

## B. App Structure

- Public pages move into a route group `src/app/(site)/` with their own root layout (`<html lang={locale}>`, `NextIntlClientProvider`, `SiteHeader`, `SiteFooter`, GA4). **URLs are unchanged** — route groups don't appear in paths.
- `src/app/admin/` gets its own root layout (`<html lang="ko">`), so admin pages no longer inherit the visitor's locale.
- `src/app/api/` needs no layout and is untouched.
- The current single `src/app/layout.tsx` and the `PublicOnly` wrapper are removed; the split layouts make them unnecessary.
- The existing `middleware.ts` (admin session refresh, matcher `/admin/:path*`) is unchanged — this design adds no middleware.
- Moving between `(site)` and `admin` does a full page load (different root layouts). Acceptable: operators rarely cross between them.

## C. Message Files

```
src/i18n/
  locales.ts        LOCALES, Locale type, LOCALE_LABELS (native names), resolveLocale()
  request.ts        next-intl getRequestConfig
  messages/
    ko.ts           source of truth; exports `Messages = typeof ko`
    en.ts           export default { ... } satisfies Messages
    zh-CN.ts
    zh-TW.ts
    ja.ts
```

**Namespaces** (top-level keys): `common` (header, footer, switcher, not-found), `landing`, `basicInfo` (form labels, business stage labels, consent UI and notice text), `wizard` (layer descriptions, 28 questions, Likert scale labels, navigation), `result` (level copy, bottleneck/strength copy, 90-day actions, section headings, CTAs), `consult`, `privacy` (full policy text), `metadata` (page titles/descriptions).

**Moved out of `src/lib/content/`** into messages: `questions.ts`, `layer-descriptions.ts`, `architecture-level-copy.ts`, `bottleneck-copy.ts`, `strength-copy.ts`, `action-library.ts`, the labels in `business-stage.ts`, and `privacy-notice.ts` text. `summary.ts` becomes a function that takes the translator. `PRIVACY_NOTICE_VERSION` stays a constant shared by all locales. `mask-email.ts` and `company.ts` (section D) stay in `src/lib/content/`.

**Stays as-is in every language:** stored codes (layer IDs, `architecture_level` values, business stage values like `mvp_prep`), and the PBA layer names (VALUE, CUSTOMER, OFFER, EXPERIENCE, PROCESS, DATA & INTELLIGENCE, SCALE) — they're methodology terms. User-entered free text (business stage "other", consult messages) is shown as entered.

**Privacy policy translations** carry a notice at the top: the translation is for convenience and the Korean version prevails.

**Server vs client:** server components use `getTranslations()`; client components (`/diagnose` form, `QuestionWizard`, `ConsultForm`, `PrivacyConsentField`, the switcher) use `useTranslations()`. The `(site)` layout passes only the current locale's messages to `NextIntlClientProvider`, minus server-only namespaces (`privacy`, `metadata`), so the browser never downloads other locales.

**Admin reuse:** `ResultReport` takes an explicit `locale` prop and calls `getTranslations({ locale, namespace })`. The public result page passes the visitor's locale; the admin result popup passes `"ko"`. Admin business-stage labels read the `ko` messages directly.

## E. Stored Data (migration `0010_add_locale.sql`)

- Add `locale text not null default 'ko'` to `assessment_drafts` and `assessments`, constrained to the five locales. Existing rows become `ko`.
- `POST /api/assessment-drafts` records the request's resolved locale on the draft; completing the draft copies it onto the assessment. The direct `POST /api/assessments` route records it too.
- The result page always renders in the **viewer's** locale; the stored `locale` is for operators (which language to contact the person in) and for Phase 2 PDF/email.
- Admin consulting-request and assessment list/detail pages show a "언어" field, e.g. `日本語 (ja)`.
- `privacy_notice_version` stays shared across locales; any change to the notice updates all five locales and bumps the version.

## F. Language Switcher

- A trigger at the right of the site header: globe icon + current language's native name (e.g. `🌐 日本語`).
- Opens a shared `Dropdown` component (`src/components/ui/Dropdown.tsx`) anchored directly below the trigger, right-aligned to it, clamped inside the viewport on narrow screens. White card, border, shadow, rounded corners; the current locale shows a ✓ on a highlighted row. Options are native names: 한국어, English, 简体中文, 繁體中文, 日本語.
- Closes on outside click or Escape; arrow keys move, Enter selects; the trigger has `aria-haspopup="listbox"`/`aria-expanded`.
- Selecting writes `NEXT_LOCALE` (path `/`, 1 year, `SameSite=Lax`) and calls `router.refresh()` — the page re-renders in the new language in place. Mid-diagnosis answers are safe; they live in the server-side draft.

## G. Testing

- **Unit (Vitest):** `resolveLocale` — cookie precedence, q-value ordering, unsupported entries skipped, every Chinese mapping, country fallback including "other country → en", and the all-empty → `ko` case.
- **Translation completeness:** enforced by `satisfies Messages` in each locale file; `npm run typecheck` and `npm run build` fail on a missing key.
- **Existing tests** that assert Korean copy from `src/lib/content/` are updated to read from `ko` messages.
- **Manual (dev server):** request `/`, `/diagnose`, a result page, its consult page, and `/privacy` with each of: a `NEXT_LOCALE` cookie per locale, `Accept-Language` values per locale (including `zh-HK` and `fr, en;q=0.8`), a `CloudFront-Viewer-Country` header alone, and no headers. Confirm `<html lang>`, visible copy, the English company block on non-`ko` locales, and the `Vary` header. Confirm `/admin` stays `lang="ko"` and its result popup stays Korean. Complete one diagnosis in `ja` and confirm the admin shows `日本語 (ja)`.
- **After deployment:** check on pba.ylia.io whether `CloudFront-Viewer-Country` reaches the app (temporary log or debug response), and that CloudFront varies correctly.

## Explicitly Out of Scope

- Translating the admin panel.
- Per-language URLs, `hreflang`, or per-language search indexing.
- Translating emails or PDFs (Phase 2 will use the stored `locale`).
- Native-speaker review workflow or a translation management service.
